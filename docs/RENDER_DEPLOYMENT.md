# Deploy UniStay on Render (free testing environment)

This adds **Docker deployment only**. Existing local development still uses:

```powershell
php -S localhost:8000 -t frontend
```

## 1. Before deployment

- Do **not** include any actual secrets or `config/*.local.php` files in Git.
- Back up the database before inviting real visitors. The hosted app accesses the **same TiDB database** as localhost.
- Make sure current user-facing routes work locally, not just the homepage.
- `frontend/public/index.php` must be present. All browser CSS/JS/image links should be absolute from `frontend/`, such as `/src/styles/style.css`.
- If your project still uses `config/db_connect.php`, verify that it uses the **same TiDB credentials** as `backend/includes/database.php`. This kit does **not** overwrite that legacy connector, because its current implementation was not available for review.
- Verify `composer.json` and `composer.lock` are committed if Google's PHP auth library requires them.
- Check the Google authentication backend accepts the `config/google.local.php` values generated by the kit; if it expects additional fields, adapt the generation script accordingly.
- Do not deploy unfinished or experimental admin pages. Make sure each admin endpoint enforces an admin role and CSRF checks.

## 2. Add the files to the repository

Extract the zip into the root of UNISTAY, keeping `Dockerfile`, `.dockerignore`, and `docker/` alongside `frontend/`, `backend/`, and `config/`.

```powershell
git switch main
git pull --ff-only origin main
git switch -c deploy/render-free
git add Dockerfile .dockerignore docker docs/RENDER_DEPLOYMENT.md
git diff --cached --check
git diff --cached --name-only
git commit -m "chore: prepare PHP application for Render deployment"
git push -u origin deploy/render-free
```

For a first test, deploy Render directly from the `deploy/render-free` branch. Once the site works and your teammates review the changes, merge the branch into `main` and update Render to deploy `main`. This avoids disrupting their work.

## 3. Create a Render Web Service

1. Go to https://dashboard.render.com and create an account or sign in.
2. Choose **New → Web Service**, then connect your GitHub repo `baby-sharks1/UNISTAY`.
3. Select branch `deploy/render-free` for the initial test (switch to `main` after reviewing and merging).
4. Set the runtime to **Docker** (Render does not have a native PHP runtime).
5. Set the plan to **Free**, choose a nearby available region, and leave the Dockerfile path as `./Dockerfile`.
6. Set the environment variables listed below, using Render's secret/environment settings rather than storing them in the repo.
7. Create the service. Render will build a PHP/Apache container and assign an HTTPS URL ending in `.onrender.com`.

## 4. Render environment variables

| Name | Value | Required |
| --- | --- | --- |
| `TIDB_HOST` | Existing TiDB host name **without** `mysql://` | Yes |
| `TIDB_PORT` | `4000` (unless TiDB configured otherwise) | Optional (defaults to 4000) |
| `TIDB_DATABASE` | `UNISTAY` or your actual database name | Yes |
| `TIDB_USERNAME` | Existing TiDB database user | Yes |
| `TIDB_PASSWORD` | Existing TiDB database password | Yes |
| `TIDB_CA_PEM_BASE64` | Base64 of the **trusted CA PEM** if the system CA bundle does not validate TiDB | Optional |
| `CLOUDINARY_CLOUD_NAME` | Cloudinary cloud name | Required for uploads |
| `CLOUDINARY_API_KEY` | Cloudinary API key | Required for uploads |
| `CLOUDINARY_API_SECRET` | Cloudinary API secret | Required for uploads |
| `GOOGLE_CLIENT_ID` | Google OAuth **Web** client ID | Required for Google login |
| `GOOGLE_CLIENT_SECRET` | Only if used by your existing OAuth backend | Optional |
| `UNISTAY_ADMIN_EMAIL` | The **previously provisioned** admin email | Needed for admin password login |

Do not add an admin password to Render environment variables. Provision the administrator **once** from a trusted machine using `php scripts/provision_admin.php` against the same TiDB database. Runtime startup creates an email allowlist, not a new admin or password.

If TiDB requires a custom CA, encode the trusted PEM locally in PowerShell:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes('C:\path\to\TiDB-ca.pem'))
```

Paste that result in Render's `TIDB_CA_PEM_BASE64` environment field. The certificate contains no account password; still keep the original connection material managed privately. TLS certificate verification remains **enabled**.

## 5. Enable Google Sign-In on the public domain

In Google Cloud Console → APIs & Services → Credentials → your **Web** OAuth client:

- Add the **exact** `https://YOUR-SERVICE.onrender.com` to **Authorized JavaScript origins**.
- If your chosen OAuth flow uses a browser redirect, register the exact HTTPS callback under **Authorized redirect URIs** too. Google Identity Services' button-with-ID-token flow may not need a redirect URI.
- If the OAuth consent screen is in Testing mode, add permitted test users.
- Do not remove `http://localhost:8000` if local development still needs it.

## 6. Open and test the app

- Homepage: `https://YOUR-SERVICE.onrender.com/` (redirects to `/public/index.php`)
- Browse: `/public/listings.php`
- Login: `/public/login.php`
- Register: `/public/register.php`
- Student dashboard: `/student/dashboard.php`
- Owner dashboard: `/owner/dashboard.php`
- Admin dashboard: `/public/admin/dashboard.php`

Test with **disposable student/owner accounts** first. Confirm public listing photos load, Google and password login work, inquiries reach owners, and role permissions prevent access to admin pages.

## 7. Expected limitations and troubleshooting

- **Cold start:** Render Free goes to sleep after 15 minutes idle. The first request later can take approximately a minute.
- **Ephemeral sessions:** Local PHP session files disappear on restart/spin-down. Users may have to log in again. For reliable long-lived sessions, add a persistent shared session store in a later phase.
- **Ephemeral files:** Do not store listing images on the Render filesystem. Use Cloudinary. TiDB data persists separately.
- **Database timeout:** Check TiDB cluster state, outbound network, IP access policies, host/port 4000, and CA verification. Never disable verification.
- **Database config missing:** Verify all four required TiDB env vars are entered into Render's dashboard and read the Render deploy logs. The startup script intentionally fails instead of running without DB configuration.
- **Composer build failure:** Check that dependencies support PHP 8.5 and extensions. Run `composer install` and `composer check-platform-reqs` locally.
- **Legacy database connector:** If a page still refers to `config/db_connect.php` with stale settings, update that connector to call `db()` safely; the Render environment only generates `config/database.local.php`.
- **PHP syntax issue:** Run `php -l` locally for modified PHP files.
- **Google login 403:** Check JavaScript origins, backend credential verification and PHP session/CSRF token checks.
- **Admin account:** Never use a public demonstration password, never expose `scripts/provision_admin.php` over HTTP, and disable/admin-limit access if the UI hasn't passed authorization tests.

## 8. Public safety before sharing broadly

This is a test deployment, not a security audit. The shared database could contain personal information; prefer a **separate demo database** and temporary test accounts. Protect personally identifying details, harden session/account controls, review every destructive admin action, and rotate any old secrets exposed in Git history. Set reasonable quotas on Cloudinary and TiDB, and monitor Render's bandwidth and free-instance usage.
